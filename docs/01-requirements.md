# 요구사항

## 1. 목적

Windows Server 환경에 분산 저장된 설비 관련 파일을 클라이언트에 제공한다.

초기 제공 대상은 **설비 로그 파일**이며, 이후 로그 외 추가 파일도 같은 기반 기능을 사용해 제공할 수 있어야 한다.

## 2. 클라이언트 환경

- 카운터파트너 서버
- 일반 로컬 PC
- Windows / Linux 혼재
- 지원 기술 스택
  - .NET
  - Python / FastAPI

클라이언트는 특정 OS 또는 Windows 전용 프로토콜에 종속되지 않아야 한다.

## 3. 서버 및 파일 분산 구조

- 로그 서버는 공정 및 설비 단위로 분산되어 있다.
- 설비와 실제 서버의 매핑 기준정보를 이미 보유하고 있다.
- 클라이언트는 이 분산 구조를 알 필요가 없다.
- 클라이언트는 **설비명**을 기준으로 요청한다.
- 서버 측에서 기준정보를 사용해 실제 대상 서버 및 파일 위치를 결정한다.

## 4. 파일 경로 기준정보

- 로그 종류별로 서버 내 저장 위치가 다르다.
- 로그 종류별 경로 및 관련 기준정보는 MSSQL에 존재한다.
- FileGateway는 MSSQL Stored Procedure를 통해 필요한 경로 정보를 전달받는다.
- 실제 경로 규칙을 API 코드에 하드코딩하지 않는다.

## 5. 로그 종류 및 조회 조건

### 5.1 시간 단위 로그

- 시간 단위로 파일이 생성된다.
- 특정 일자, 특정 시간 또는 시간 범위로 조회할 수 있어야 한다.

### 5.2 일 단위 로그

- 일 단위 파일이 존재한다.
- 특정 일자 또는 일자 범위로 조회할 수 있어야 한다.

### 5.3 계속 갱신되는 로그

- 파일이 지속적으로 갱신되는 형태다.
- 날짜/시간 필터와 무관하게 현재 존재하는 해당 파일을 목록에 포함한다.

## 6. 클라이언트 인터페이스 원칙

- 실제 전송 방식은 HTTP/HTTPS 기반 API를 사용한다.
- 메타데이터 응답은 JSON을 기본으로 한다.
- 파일 다운로드는 스트리밍 방식으로 제공한다.
- .NET 및 Python 클라이언트에서 익숙하게 사용할 수 있도록 유명 FTP 라이브러리의 사용 패턴을 차용한다.
- FTP의 세션/디렉터리/Passive Mode 등 프로토콜 종속 개념은 그대로 복제하지 않는다.

주요 사용 패턴 예:

- 목록 조회
- 파일 존재 여부 확인
- 파일 크기 조회
- 파일 다운로드

## 7. 추상화 원칙

클라이언트에는 다음 정보를 노출하지 않는다.

- 실제 서버명/IP
- 공정별 서버 분산 구조
- 실제 서버 내 물리 디렉터리
- DB 기준정보 구조

클라이언트는 설비명과 논리적 조회 조건만 사용한다.

## 8. 확장성 요구사항

- 로그 제공 기능은 공통 서버/파일 접근 기능과 분리한다.
- 공통 계층은 `Log`라는 도메인 개념에 종속되지 않는다.
- 이후 설정 파일, 리포트 파일, 추가 설비 파일 등의 Provider를 추가할 수 있어야 한다.

## 9. 현재 미정 사항

다음 항목은 후속 설계에서 확정한다.

- FileGateway 서버 구현 기술 스택
- 인증/인가 방식
- 네트워크 구간 및 방화벽 정책
- 최대 파일 크기 및 동시 다운로드 제한
- 부분 다운로드/재개 지원 여부
- 파일 보존기간
- API 버전 정책
- 상세 오류 코드
