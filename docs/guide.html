01 · PROJECT OVERVIEW

FileGateway가 뭔가요

분산 파일 서버에 이미 저장돼 있는 설비 로그와 Configuration File을, 실제 서버 주소나 물리 경로를 몰라도 equipmentId와 논리 조회 조건만으로 꺼내 쓸 수 있게 해주는 읽기 전용 게이트웨이입니다.

WPF 데스크톱 앱, Web Backend, 다른 서버 시스템이 각자 FTP 서버 주소나 폴더 구조를 알 필요 없이, HTTPS + API Key로 FileGateway 하나만 호출하면 됩니다. 어떤 설비가 어떤 서버에, 어떤 규칙으로 파일을 두는지는 MSSQL 기준정보가 알고 있고, FileGateway가 그 규칙을 해석해 FTP/FTPS(또는 같은 머신이면 로컬 파일시스템)에서 파일을 읽어 스트리밍으로 내려줍니다.

범위 밖 설비에 직접 접속하거나, 로그를 수집/가공하거나, Configuration History를 새로 만들고 복사·보관하는 일은 다른 시스템의 책임입니다. FileGateway는 이미 저장된 파일을 읽어서 제공할 뿐입니다.

설계 원칙

물리 정보 비노출

서버 주소·경로·credential은 API 응답 어디에도 나타나지 않습니다.

동일 Resolver

목록 조회와 조건부 직접 다운로드가 같은 탐색 규칙을 씁니다 — 결과가 어긋나지 않습니다.

스트리밍 우선

파일을 메모리에 통째로 올리지 않고, 시작 시점 크기를 Content-Length로 흘려보냅니다.

DB로 확장

새 설비·로그종류는 대부분 코드 배포 없이 기준정보 등록만으로 노출됩니다.

현재 상태

MVP 구현이 완료되어 단위·통합 테스트를 전부 통과한 상태입니다. 실제 운영 배포는 배포 체크리스트의 수동 검증 항목을 통과해야 완료로 간주합니다 — 자동화 테스트가 이 검증을 대체하지 않습니다.

02 · API 사용자 가이드

API로 파일 받아오기

HTTPS와 X-Api-Key 헤더만 있으면 됩니다. 브라우저가 API Key를 직접 들고 있는 구조는 상정하지 않으므로, 서버-서버 또는 데스크톱 클라이언트 환경(.NET, Python 등 일반 HTTP 클라이언트)에서 호출하세요.

X-Api-Key: <caller-key>

Key는 header로만 전달합니다. query string에 실으면 인증되지 않습니다. 누락·불일치는 모두 401 InvalidApiKey입니다.

권장 호출 순서

  1. API Key 발급받기 — 운영자에게 요청, X-Api-Key 헤더로만 사용
  2. 설비 목록 확인 — GET /api/v1/equipments로 전체 equipmentId 조회
  3. 제공 종류 확인 — GET /api/v1/equipments/{id}/file-types로 그 설비가 주는 logType/configurationType 확인
  4. 목록 또는 조건부 조회 — 로그는 /logs, Configuration은 /configurations/current 또는 /history
  5. 파일 1건으로 확정되면 바로 다운로드 — /logs/download 또는 /configurations/current/download. 2건 이상이면 409가 나므로 목록에서 골라야 합니다
  6. 목록에서 고를 땐 fileId로 — /files/download?fileId=... (공통 다운로드 엔드포인트)
왕복을 줄이는 팁 파일이 정확히 1건으로 좁혀질 조건(예: 시간 범위를 1시간 단위로)이면 목록 조회 없이 조건부 다운로드로 바로 가는 편이 요청 수를 줄입니다.

엔드포인트 한눈에 보기

메서드/경로설명응답 형태

전체 파라미터·정렬·pagination 규칙은 저장소의 docs/05-api-interface.md가 기준입니다. 이 페이지는 실무에서 바로 쓰는 요약입니다.

시간 범위 규칙

  • Hourly/Daily — from/to 둘 다 생략하면 최근 2일. from만 있으면 [from, from+2일).
  • Continuous — from/to를 주면 400. 현재 파일만 조회됩니다.
  • 다음 페이지는 같은 조건 + continuationToken만 추가. 토큰을 유지한 채 조건을 바꾸면 400입니다 — 조건을 바꾸려면 토큰 없이 처음부터 다시 조회하세요.

fileId, 재사용 가능한 opaque 토큰

fileId는 목록/조건부 다운로드 응답에서 발급되는 24시간짜리 opaque 토큰입니다. 물리 경로가 아니라 논리 파일을 가리키므로, 그 사이 서버 쪽 물리 배치가 바뀌어도 같은 논리 파일이면 그대로 유효합니다. 접근할 때마다 현재 기준정보로 물리 위치를 다시 계산합니다.

호출 예시

로그 목록 조회 → fileId로 다운로드

# 1. 목록 조회 (+09:00 은 %2B09:00 으로 URL-encoding)
curl -s "https://gateway.example/api/v1/logs?equipmentId=EQ-001&logType=EventLog&from=2026-08-20T00:00:00%2B09:00&to=2026-08-21T00:00:00%2B09:00" \
  -H "X-Api-Key: $API_KEY"

# 2. 응답의 items[0].fileId 로 스트리밍 다운로드
curl -s -OJ "https://gateway.example/api/v1/files/download?fileId=$FILE_ID" \
  -H "X-Api-Key: $API_KEY"

Python (requests) 핵심 패턴

def download_by_file_id(file_id: str, file_name: str, dest_dir=".") -> str:
    dest = os.path.join(dest_dir, os.path.basename(file_name))
    with requests.get(f"{GATEWAY}/api/v1/files/download", headers=HEADERS,
                       params={"fileId": file_id}, stream=True, timeout=(10, 60)) as resp:
        resp.raise_for_status()
        expected = int(resp.headers.get("Content-Length", -1))
        written = 0
        with open(dest, "wb") as f:
            for chunk in resp.iter_content(chunk_size=1024 * 64):
                f.write(chunk); written += len(chunk)
        if expected >= 0 and written != expected:
            # 원격 I/O 오류는 JSON 오류로 전환되지 않고 스트림이 끊긴다 — 바이트 수를 직접 비교
            raise IOError(f"truncated: expected {expected}, got {written}")
    return dest

전체 8개 유즈케이스별 Python/C# 예제는 저장소 samples/에 있습니다.

오류 코드

모든 오류는 { type, title, status, code, traceId } 형태입니다. code로 분기하고, 원인 추적은 traceId로 서버 로그와 연계하세요. 물리 경로·credential은 어떤 오류 응답에도 포함되지 않습니다.

statuscode의미

400InvalidFileIdfileId 형식·서명 오류
401InvalidApiKeyX-Api-Key 누락·불일치
404EquipmentNotFound존재하지 않는 equipmentId
404LogDefinitionNotFound / ConfigurationDefinitionNotFound기준정보 삭제로 재해석 불가

502FileServerUnavailable / FileServerProtocolError파일 서버 연결·프로토콜 오류
503ReferenceDataUnavailable사용 가능한 기준정보 없음
03 · 서버 관리자 가이드

배포하고 운영하기

FileGateway는 코드와 별개로 MSSQL 기준정보가 "어떤 설비가 어떤 서버의 어떤 규칙으로 파일을 제공하는지"를 정의합니다. 새 설비·로그종류 추가는 대부분 DB 등록만으로 끝나고 코드 배포가 필요 없습니다.

사전 준비물

.NET 10 SDK

global.json 고정 버전. dotnet --version으로 확인.

MSSQL + SP

FileGateway_GetReferenceData (db/mvp-stored-procedure.sql)

FTP/FTPS 접근

단일 머신 구성은 서버를 localhost로 등록하면 FTP 없이 로컬 파일시스템 직접 접근.

IIS Hosting Bundle

ASP.NET Core Module V2, In-process 호스팅.

dotnet test                              # 단위 + 통합(Testcontainers)
dotnet run --project src/FileGateway.Api # 기본 http://localhost:5178

비밀 주입 · API Key 회전

비밀은 파일에 두지 않고 환경변수(또는 IIS/Secret 관리 도구)로만 주입합니다.

환경변수용도
Authentication__ApiKeys__0__Key / __CallerIdAPI Key(복수 호출자는 인덱스 1, 2...)
ConnectionStrings__ReferenceDataMSSQL 기준정보 연결 문자열
FileGateway__Ftp__UserName / __PasswordFTP 계정
DataProtection__KeyDirectory토큰 보호 키 저장 디렉터리 — Development 외 환경은 미설정 시 기동 자체가 실패

Key overlap 회전

# 구 key(index 0) 유지한 채 신규 key(index 1) 추가 → 재배포
Authentication__ApiKeys__0__Key=<old-key>
Authentication__ApiKeys__0__CallerId=wpf-client
Authentication__ApiKeys__1__Key=<new-key>
Authentication__ApiKeys__1__CallerId=wpf-client
# 클라이언트 전환 확인 후 index 0 제거 → 재배포
IIS Application Pool — Load User Profile 토큰 보호 키는 Windows에서 DPAPI로 current-user 범위(App Pool identity) 보호됩니다. 이게 동작하려면 App Pool의 "Load User Profile"을 반드시 true로 설정해야 합니다(applicationHost.config 수준 — web.config로 제어 안 됨). DataProtection:KeyDirectory가 App Pool 재시작 후에도 유지되는 경로가 아니면 모든 fileId가 무효화됩니다.

기준정보 운영

기준정보 담당자가 MSSQL에 설비/로그종류/구성종류를 등록하면, 다음 요청 또는 캐시 TTL(기본 15분) 만료 시 FileGateway가 자동으로 새로 읽어옵니다.

sequenceDiagram
    participant Op as 기준정보 담당자
    participant SP as MSSQL SP
    participant GW as FileGateway
    participant Cache as ReferenceData Cache
    Op->>SP: 신규 설비 / logType / configurationType 등록
    Note over GW,Cache: 다음 요청 또는 CacheTtl(15분) 만료 시
    GW->>SP: FileGateway_GetReferenceData 호출
    SP-->>GW: 서버/설비/로그정의/구성정의
    GW->>GW: 구조 validation
    alt 검증 성공
        GW->>Cache: 전체 atomic 교체
    else 검증 실패(정의 1건이라도 위반)
        GW->>Cache: 기존 last-known-good 유지
    end
  • 검증 실패는 전체 refresh 거부가 아니라, 개별 정의만 격리됩니다 — 잘못된 정의 1건이 나머지 정상 설비까지 막지 않습니다.
  • refresh는 FTP 서버 실재 여부를 확인하지 않습니다. 파일이 실제로 있는지는 목록/다운로드 시점에만 확인합니다.
  • 최초 기동 시 usable 캐시가 없으면 /health/ready가 503 ReferenceDataUnavailable — DB 연결/SP 존재부터 확인하세요.
  • 기존 계약(Hourly/Daily/Continuous/Current/History)으로 표현 가능한 신규 종류는 코드 수정 없이 DB 등록만으로 노출됩니다.

Health Check · 감사 로그

엔드포인트의미
GET /health/live프로세스 생존 여부만. 기준정보 DB 장애만으로 실패하지 않음. 인증 불필요.
GET /health/ready검증 완료 기준정보 확보 여부 포함. 마지막 정상 캐시가 있으면 DB 장애 중에도 stale로 200(Degraded) 유지.

감사 로그는 timestamp · callerId · client IP · endpoint · equipmentId · logType/configurationType · fileId · fileName/fileSize · 성공/실패 · elapsedMs를 남깁니다. API Key 원문·FTP credential·물리 경로·token 내부 payload는 절대 기록하지 않습니다.

배포 전 필수 확인 (요약)

실 배포는 dotnet build && dotnet test 자동화 게이트를 넘어, 실제 Windows Server + IIS + MSSQL + 파일 서버 환경에서의 수동 검증을 거쳐야 완료로 간주합니다. 전체 체크리스트는 저장소 docs/DEPLOYMENT-CHECKLIST.md — 아래는 그중 놓치기 쉬운 항목입니다.

  • 여러 X-Api-Key 인증/호출자 구분 + query string key 거부(401 실제 확인)
  • API Key 신/구 overlap 회전(두 key 동시 활성 → 구 key 폐기)
  • 기준정보 개별 invalid 정의 격리(잘못된 정의 1건 주입 → 정상 정의는 그대로 유지되는지)
  • DataProtection 키의 IIS 재시작 내구성(재시작 후 기존 fileId가 여전히 유효한지)
  • rootPath 경계/traversal 차단(경계 위반 정의 주입 → 해당 정의만 격리)
  • 로그/감사로그에 API Key·FTP credential·물리 경로가 실제로 안 남는지 샘플 검토
