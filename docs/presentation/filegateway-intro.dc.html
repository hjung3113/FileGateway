FileGateway 안내 — 설비 파일을 논리 조회 조건으로 내려받는 읽기 전용 게이트웨이

FileGateway(읽기 전용 파일 제공 게이트웨이)는 분산 파일 서버에 이미 저장된 설비 로그와 설정 파일(Configuration File)을 조회하고 내려받게 해 준다. API 사용자(클라이언트 개발자)는 파일 서버 주소와 물리 경로를 몰라도 설비 식별자(equipmentId)와 논리 조회 조건만으로 호출한다. 구현은 끝났고, API 제공자(운영자)가 배포 전 필수 확인 20개 항목을 통과해야 MVP가 완료된다.

01 · 개요

개요 — 두 독자가 쓰는 하나의 입구

FileGateway는 설비가 만든 로그와 설정 파일을 읽기 전용으로 내주는 입구다. 호출하는 쪽은 equipmentId와 논리 조회 조건만 알면 되고, 파일 서버 주소와 물리 경로는 몰라도 된다. 쓰는 사람은 둘로 나뉜다. API 사용자는 WPF 앱과 Web Backend/BFF, 파일을 받아 가는 다른 서버이며 .NET이나 Python 같은 일반 HTTP 클라이언트로 호출한다. API 제공자는 기준정보(Reference Data)와 파일 서버를 등록하고 FileGateway를 배포하고 운영한다.

02 · 범위

범위 — 하는 일과 하지 않는 일

범위 밖의 일은 FileGateway가 못 하는 일이 아니라 설계상 다른 시스템이 맡는 일이다. 별도 시스템이 파일을 만들어 파일 서버에 저장하고, FileGateway는 파일 서버에 보이는 파일을 읽어 내준다. MVP에서 뺀 항목은 13개이며 표는 이를 묶음별로 보여 준다. 후속 확장은 실제 요구가 생길 때 판단하고, 지금은 구현하지 않는다.

03 · 원칙

설계 원칙 — 물리 구조를 감추는 여섯 가지

호출하는 쪽이 기대해도 되는 보장은 여섯 가지다. 모두 설계 지침이면서 코드로 확인된 동작이다. 호출하는 쪽이 알아야 할 것은 논리 조회 조건뿐이고, 파일이 어디에 어떻게 저장돼 있는지는 FileGateway 안에 머문다.

1물리 정보 비노출
서버 주소와 물리 경로는 성공 응답과 오류 응답 어디에도 나오지 않는다.
2경로를 입력으로 만들지 않음
파일 접근은 서버의 루트 경로(rootPath) 아래로 정규화한 경로만 쓴다.
3스트리밍
파일을 메모리에 올리지 않고 시작 직전에 확인한 크기로 내려 보낸다.
4같은 Resolver
목록 조회와 다운로드 요청이 같은 규칙으로 파일을 찾는다.
5오류 구분
기준정보 없음, 파일 서버 접근 실패, 경로 없음, 파일 없음을 한 오류로 뭉개지 않는다.
6읽기 전용
저장된 파일을 읽어 줄 뿐 생산 중 파일의 일관성은 보정하지 않는다.
→ 물리 구조를 아는 쪽은 FileGateway뿐이다.

04 · 파일

제공 파일 — 설비가 내놓는 두 갈래

설비는 표시명과 다른 안정적인 논리 식별자 equipmentId로 가리키며, 이 값은 한 배포 범위 안에서 유일하다. 한 설비가 내놓는 파일은 로그와 설정 파일 두 갈래다. 로그 종류(logType)는 업무로 나눈 분류이고, 로그 종류 하나에 생성 유형(generationType) 하나가 붙는다. 생성 유형은 Hourly, Daily, Continuous 세 가지다. 설정 파일은 로그가 아니며, 설정 파일 종류(configurationType) 아래에 현재 설정 파일(Current)과 설정 파일 이력이 놓인다.

참고설비마다 내놓는 파일이 달라도 기준정보의 차이로 표현하며, 설비사 전용 분기는 없다.
05 · 호출

호출 순서 — 설비 목록에서 파일 수신까지

호출은 API Key로 시작한다. 인증은 X-Api-Key 헤더로만 하고, 헤더가 없거나 값이 맞지 않으면 모두 401 InvalidApiKey다. 이어서 설비 목록과 제공 종류, 파일 목록을 차례로 조회한다. 조건만으로 받을 파일이 정해지면 목록을 건너뛰고 조건 기반 직접 다운로드를 쓴다. 그렇지 않으면 목록에서 받은 fileId(24시간 유효한 opaque 토큰)로 /files/download를 부른다. 결말은 네 가지다.

06 · 흐름

호출 흐름 — 목록 조회에서 스트리밍까지

목록 요청과 다운로드 요청이 FileGateway 안에서 처리되는 순서를 보면, 호출하는 쪽이 믿어도 되는 동작이 드러난다. 목록 요청은 인증 뒤에 기준정보 캐시에서 서버와 탐색 규칙(discovery rule)을 읽고, 파일 서버에서 받은 디렉터리 목록을 돌려준다. 응답에는 items와 fileId, continuationToken(다음 페이지 커서)이 담긴다. 이 커서는 서버에 결과를 저장하지 않는 stateless 방식이고 유효기간은 30분이다. 다운로드 요청은 현재 기준정보로 물리 경로를 다시 계산하므로, 서버나 경로가 바뀌어도 같은 논리 파일이면 기존 fileId가 유효하다.

07 · 시간 범위

시간 범위 규칙 — Hourly·Daily와 Continuous

조회 범위는 로그 종류의 생성 유형과 from, to 입력으로 정해지고, 조건이 맞지 않으면 InvalidRequest가 된다. 시간 값은 반개구간 [from, to)로 읽는다. from은 포함하고 to는 제외한다. 표에서 첫 칸이 아니오이면 Hourly나 Daily 로그다. 이 두 유형은 범위가 MaxQueryRange(기본 31일)를 넘어도 InvalidRequest이며, 이 값은 2일 이상이어야 한다. offset이 없는 시간 값은 Asia/Seoul로 읽는다.

08 · 오류

오류 응답 — 14종의 code

호출하는 쪽은 HTTP 상태가 아니라 code로 분기한다. 오류 code는 14종이고, 응답 본문에는 type, title, status, code, traceId가 담긴다. 원인을 추적할 때는 traceId로 서버 로그와 잇는다. 물리 경로와 credential, DB 진단은 응답에 없다. 클라이언트가 요청을 끊으면 서버가 ClientCancelled로 기록하지만 이는 응답 code가 아니다.

09 · 구조

시스템 구조 — 네 층과 외부 자원

파일 제공 경로는 네 층이고, 호출하는 쪽은 맨 위 Api 층만 알면 된다. Core는 IFileAccess 계약과 token codec 계약만 두고 로그, 설정 파일, FTP, MSSQL, IIS를 모른다. 파일 접근은 FtpFileAccess와 LocalFileAccess 둘이고 RoutingFileAccess가 호출마다 서버 host로 하나를 고른다. host가 정확히 localhost일 때만 로컬 디스크로 가고, 127.0.0.1, ::1, 머신명, FQDN은 모두 FTP다. 외부 자원은 MSSQL과 파일 서버(localhost면 로컬 파일시스템)다.

10 · 모델

기준정보 모델 — 설비·서버·정의의 관계

기준정보는 API 제공자가 MSSQL에 등록하는 정의 모음이고, 저장 프로시저 FileGateway_GetReferenceData가 result set 네 개로 돌려준다. 네 개는 설비, 파일 서버, 로그 정의(Log Definition), 설정 파일 정의(Configuration Definition)다. 로그 정의는 설비의 로그 종류 하나를 서버와 탐색 규칙에 잇는 한 건이고, 설정 파일 정의는 설정 파일 종류 하나를 같은 방식으로 잇는다. 정의는 모두 존재하는 설비와 서버를 가리켜야 한다. 그렇지 않거나 같은 키가 여러 행이면 그 정의는 invalid다. 생성 슬롯은 Hourly는 한 시간, Daily는 하루로 나눈 논리 구간이며 물리 폴더와 1대 1이 아니다.

11 · 갱신

기준정보 갱신 — 검증 단계와 마지막 정상본

기준정보 캐시는 CacheTtl(기본 15분)이 지나면 갱신을 다시 시도하지만, 요청이 갱신을 기다리지는 않는다. 갱신은 프로세스당 하나만(single-flight) 돌고, 전역 검증과 정의별 검증의 두 단계를 거쳐 결말이 네 가지로 갈린다. 전역 검증이 실패하면 새 데이터를 통째로 거부하고 마지막 정상본(last-known-good)을 stale 상태로 계속 쓰며, 통과하면 틀린 정의만 빼고 교체한다. stale에는 최대 시간 제한이 없으므로 stale 사용 여부와 마지막 정상 갱신 시각을 관측해야 한다.

12 · 이력

설정 파일 이력 — 완료 marker와 인계

설정 파일 이력은 FileGateway가 만들지 않고 별도 시스템이 만든다. 별도 시스템이 자정에 현재 설정 파일 집합을 날짜 폴더로 복사해 스냅샷을 만들고, 복사를 마치면 완료 marker를 만든다. marker의 이름과 위치는 기준정보의 history 규칙이 정한다. FileGateway는 marker가 있는지만 보고 내용은 읽지 않으며, marker가 있는 날짜 폴더의 스냅샷만 조회 대상으로 삼는다. 복사 중인 폴더와 marker 파일 자체는 결과에 나오지 않는다.

현재 상태 — 구현 완료와 배포 확인 대기

MVP 구현은 끝났고 통합 검증 단계를 거쳤다. README는 단위·통합 테스트가 전부 통과했다고 적는다. 그러나 자동화 게이트는 구현 완료의 조건일 뿐 MVP 완료가 아니다.
