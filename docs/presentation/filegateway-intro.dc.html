FileGateway 안내 — 설비 파일을 논리 조회 조건으로 내주는 읽기 전용 게이트웨이

FileGateway(읽기 전용 파일 제공 게이트웨이)는 분산 파일 서버에 이미 저장된 설비 로그와 설정 파일(Configuration File)을 조회하고 내려받게 해 준다. API 사용자(클라이언트 개발자)는 파일 서버 주소와 물리 경로를 몰라도 설비 식별자(equipmentId)와 논리 조회 조건만으로 호출한다. 구현은 끝났고, API 제공자(운영자)가 실제 환경에서 배포 전 필수 확인 20개와 MVP 완료 기준 10개를 통과해야 MVP가 완료된다.

01 · 개요

개요 — 두 사용자가 쓰는 하나의 입구

FileGateway는 설비가 만든 로그와 설정 파일을 읽기 전용으로 내주는 입구다. 쓰는 사람은 둘로 나뉜다. API 사용자는 WPF 앱, Web Backend/BFF, 다른 서버를 만드는 개발자로, equipmentId와 논리 조회 조건만 알면 된다. 파일 서버 주소나 물리 경로, FTP 계정 없이 API Key 하나로 호출하며, .NET이나 Python의 일반 HTTP 라이브러리를 쓰면 된다. API 제공자는 기준정보(Reference Data)와 파일 서버를 등록하고, FileGateway를 배포해 운영한다. 기존 계약으로 표현할 수 있는 새 로그 종류와 설정 파일 종류는 기준정보만 등록하면 노출된다.

02 · 범위

범위 — 하는 일과 하지 않는 일

MVP 제외 항목은 13개이고, 표는 이를 묶음별로 보여 준다. 그중 설비 접속, 파일 생산, 이력 생성은 FileGateway가 못 하는 일이 아니라 설계상 별도 시스템이 맡는 일이다. 별도 시스템이 파일을 만들어 파일 서버에 저장하고, FileGateway는 파일 서버에 보이는 파일을 읽어 내준다. 나머지는 ‘지금 만들지 않음’으로 묶었으며, 실제 요구가 생길 때 판단한다.

03 · 원칙

설계 원칙 — 물리 구조를 감추는 여섯 가지

API 사용자가 기대해도 되는 보장은 여섯 가지다. 모두 설계 지침이면서 코드로 확인된 동작이다. API 사용자가 알아야 할 것은 논리 조회 조건뿐이고, 파일이 어디에 어떻게 저장돼 있는지는 FileGateway 안에 머문다.

1물리 정보 비노출
서버 주소와 물리 경로는 성공 응답과 오류 응답 어디에도 나오지 않는다.
2입력으로 경로를 만들지 않음
API 사용자가 보낸 값으로 경로를 만들지 않는다. 경로는 기준정보로만 만들고 루트 경로(rootPath) 밖으로 나가지 못하게 정규화한다.
3스트리밍
파일을 메모리에 통째로 올리지 않고 스트림으로 보낸다. 단일 파일은 전송 직전 크기를 Content-Length로 알린다.
4같은 파일 찾기 규칙
목록 조회와 다운로드는 같은 Resolver(파일을 찾는 규칙을 담은 코드)를 쓴다.
5오류 구분
기준정보 없음, 파일 서버 접근 실패, 경로 없음, 파일 없음을 한 오류로 뭉개지 않는다.
6읽기 전용
저장된 파일을 읽어 줄 뿐 생산 중 파일의 일관성은 보정하지 않는다.
→ 물리 구조를 아는 쪽은 FileGateway뿐이다.

04 · 파일

제공 파일 — 설비가 내놓는 두 갈래

설비는 표시명이 아닌 안정적인 논리 식별자 equipmentId로 구분하며, 이 값은 한 배포 범위 안에서 유일하다. 한 설비가 내놓는 파일은 로그와 설정 파일 두 갈래다. 로그 종류(logType)는 업무로 나눈 분류이고, 로그 종류 하나에 생성 유형(generationType) 하나가 붙는다. 생성 유형은 Hourly, Daily, Continuous 세 가지다. 설정 파일은 로그가 아니며, 설정 파일 종류(configurationType) 아래에 현재 설정 파일(Current)과 설정 파일 이력이 놓인다.

참고설비마다 내놓는 파일이 달라도 기준정보의 차이로 표현하며, 설비사 전용 분기는 없다.
05 · 호출

호출 순서 — 설비 목록에서 파일 수신까지

호출은 API Key로 시작한다. API Key는 X-Api-Key 헤더로만 보내고 query string으로는 받지 않는다. 헤더가 없거나 값이 틀리면 모두 401 InvalidApiKey다. 이어서 설비 목록과 제공 종류를 조회한 뒤, 조건만으로 받을 파일이 정해지면 목록을 건너뛰고 조건 기반 직접 다운로드를 쓴다. 정해지지 않거나 설정 파일 이력이면 목록에서 받은 fileId(24시간 유효한 파일 식별 토큰)로 /files/download를 부른다. 결과는 네 가지다.

06 · 처리 흐름

처리 흐름 — 목록 조회에서 스트리밍까지

아래는 FileGateway가 목록 요청과 다운로드 요청을 처리하는 순서다. 목록 요청이 오면 FileGateway는 인증한 뒤 기준정보 캐시에서 서버와 탐색 규칙(discovery rule)을 읽고, 파일 서버의 디렉터리 목록에서 조건에 맞는 파일만 골라 돌려준다. 응답은 items(항목마다 fileId 포함)와 continuationToken(다음 페이지 커서)이다. 이 커서는 서버에 결과를 저장하지 않는 stateless 방식이고 유효기간은 30분이다. 다음 페이지는 같은 조회 조건에 토큰만 더해 요청한다. 조건을 바꾸거나 토큰이 만료되면 400 InvalidRequest이므로 토큰 없이 첫 페이지부터 다시 조회한다. 다운로드 요청은 현재 기준정보로 물리 경로를 다시 계산하므로, 서버나 경로가 바뀌어도 같은 논리 파일이면 기존 fileId가 유효하다.

07 · 시간 범위

시간 범위 규칙 — Hourly·Daily와 Continuous

조회 범위는 생성 유형과 from, to로 정해지며 반개구간 [from, to)다. from은 포함하고 to는 제외한다. 범위와 비교하는 시각은 파일 수정 시각이 아니라 파일명과 경로에서 읽은 논리 시각이다. from이 to보다 앞서지 않거나 Hourly·Daily 범위가 MaxQueryRange(기본 31일)를 넘으면 InvalidRequest다. offset이 없는 시간 값은 Asia/Seoul로 읽는다.

08 · 오류

오류 응답 — 14종의 code

API 사용자는 HTTP 상태가 아니라 code로 분기한다. 오류 code는 14종이고, 응답 본문에는 type, title, status, code, traceId가 담긴다. 원인을 추적할 때는 traceId로 서버 로그와 잇는다. 물리 경로와 credential, DB 진단은 응답에 없다. API 사용자가 요청을 끊으면 서버가 ClientCancelled로 기록하지만 이는 응답 code가 아니다.

참고fileId 오류는 형식·서명 400, 24시간 경과 410, 정의 삭제 404, 파일 없음 404로 구분한다.

09 · 구조

시스템 구조 — 네 층과 외부 자원

파일 제공 경로는 네 층이고, API 사용자는 맨 위 Api 층만 알면 된다. Core는 IFileAccess 계약과 token codec(토큰을 만들고 검증하는 부분) 계약, 원격 파일 모델, 공통 I/O 오류를 둔다. Core는 로그, 설정 파일, FTP, MSSQL, IIS를 모른다. 파일 접근은 FtpFileAccess와 LocalFileAccess 둘이고 RoutingFileAccess가 호출마다 서버 host로 하나를 고른다. host가 정확히 localhost일 때만 로컬 디스크로 가고, 127.0.0.1, ::1, 머신명, FQDN은 모두 FTP다. 외부 자원은 MSSQL과 파일 서버(localhost면 로컬 파일시스템)다.

기준정보 모델 — 설비·서버·정의의 관계

기준정보는 API 제공자가 MSSQL에 등록하는 정의 모음이고, 저장 프로시저 FileGateway_GetReferenceData가 result set 네 개로 돌려준다. 네 개는 설비, 파일 서버, 로그 정의(Log Definition), 설정 파일 정의(Configuration Definition)다. 로그 정의는 설비의 로그 종류 하나를 서버와 탐색 규칙에 잇는 한 건이고, 설정 파일 정의는 설정 파일 종류 하나를 같은 방식으로 잇는다. 정의는 모두 존재하는 설비와 서버를 가리켜야 한다. 그렇지 않거나 같은 키가 여러 행이면 그 정의는 invalid(쓸 수 없는 정의)다. 생성 슬롯은 시간을 나눈 논리 구간이다. Hourly는 한 시간, Daily는 하루 단위이고 물리 폴더와 1대 1이 아니다.

11 · 갱신

기준정보 갱신 — 검증 단계와 마지막 정상본

기준정보 캐시의 CacheTtl(기본 15분)이 지난 뒤 처음 들어온 요청이 갱신을 시작한다. 그 요청은 기다리지 않고 기존 기준정보로 응답하지만, 최초 로딩에서는 요청이 결과를 기다린다. 갱신은 프로세스당 하나만(single-flight) 돌고, 전역 검증과 정의별 검증의 두 단계를 거쳐 결과가 네 가지로 갈린다. DB·SP 호출 실패도 전역 검증 실패와 같이 처리한다. 전역 검증이 실패하면 새 데이터를 통째로 거부하고 마지막 정상본(last-known-good)을 계속 쓰며, 이를 stale(갱신에 실패해 옛 값을 쓰는 상태)이라 한다. 통과하면 틀린 정의만 빼고 교체한다. stale에는 최대 시간 제한이 없으므로 stale 사용 여부와 마지막 정상 갱신 시각을 관측해야 한다.

12 · 이력

설정 파일 이력 — 완료 marker와 인계

설정 파일 이력은 FileGateway가 만들지 않고 별도 시스템이 만든다. 별도 시스템이 자정에 현재 설정 파일 집합을 날짜 폴더로 복사해 스냅샷을 만들고, 복사를 마치면 완료 marker를 만든다. marker의 이름과 위치는 기준정보의 이력 규칙(HistoryCompletionMarkerPathTemplate)이 정한다. FileGateway는 marker가 있는지만 보고 내용은 읽지 않으며, marker가 있는 날짜 폴더의 스냅샷만 조회 대상으로 삼는다. 복사 중인 폴더와 marker 파일 자체는 결과에 나오지 않는다.

엔드포인트는 /api/v1 아래 9개다. 로그 목록과 이력 목록은 items와 continuationToken을 담은 JSON이고, 현재 설정 파일 목록은 단순 배열이다. Health 두 개(/health/live, /health/ready)는 /api 밖에 있고 인증이 없다. 다운로드 세 곳(/logs/download, /configurations/current/download, /files/download)은 모두 스트림이며, 로그 직접 다운로드만 여러 건이면 zip이다.

호출 예

모든 호출은 HTTPS로 하고 X-Api-Key 헤더를 붙인다. API Key는 API 제공자가 서버 설정에 등록한 값을 쓴다. 아래 https://gateway.example은 README의 예시 값이다. 시간 값의 +09:00은 %2B09:00으로 인코딩한다.

요청 예 — 로그 목록 조회
curl -s "https://gateway.example/api/v1/logs?equipmentId=EQ-001&logType=EventLog&from=2026-08-20T00:00:00%2B09:00&to=2026-08-21T00:00:00%2B09:00&limit=50" \
-H "X-Api-Key: $API_KEY"
오류 응답 예 — 직접 다운로드나 fileId 다운로드에서 파일이 없을 때(Content-Type은 application/json)목록 조회는 일치하는 파일이 없어도 200과 빈 items를 준다.
{
"type": "about:blank",

"status": 404,
"code": "FileNotFound",

}

용어
equipmentId — 설비를 가리키는 안정적인 논리 식별자. 표시명과 다르고 한 배포 범위 안에서 유일함
생성 유형(generationType) — 로그 파일이 만들어지는 방식. Hourly, Daily, Continuous 셋 중 하나
fileId — 목록 응답의 항목마다 들어 있는 24시간 유효한 토큰. 내용을 해석하지 않고 그대로 되돌려 보내며(opaque) 물리 경로를 담지 않음
continuationToken — 목록의 다음 페이지를 가리키는 커서. 서버에 결과를 저장하지 않는 stateless 방식이며 30분 동안 유효함
기준정보(Reference Data) — MSSQL에 등록한, 어떤 설비가 어떤 파일 서버의 어떤 규칙으로 파일을 내놓는지에 대한 정의 모음
Resolver — 목록 조회와 직접 다운로드가 함께 쓰는, 파일을 찾는 규칙을 담은 코드
token codec — fileId와 continuationToken을 만들고 검증하는 부분
생성 슬롯당 파일 수(cardinality) — 생성 슬롯 하나에 파일이 몇 개까지 있을 수 있는지 정하는 규칙. Single은 최대 한 개
stale — 기준정보 갱신에 실패해 마지막 정상본을 계속 쓰는 상태
invalid — 검증에 실패해 쓸 수 없는 정의. 그 정의만 새 기준정보에서 빠짐
ARR — IIS에 붙는 요청 라우팅 모듈(Application Request Routing). 이 단계의 502와 503은 JSON이 아닐 수 있음
fileId 서명 키(DataProtection 키) — fileId와 continuationToken을 서명하고 보호하는 키. 잃으면 발급한 모든 fileId가 무효가 됨
